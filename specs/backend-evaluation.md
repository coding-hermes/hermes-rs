| Field | Value |
|---|---|

| Date | 2026-10-15 |

**Headline: no backend switch.** Turso 0.8.3 is NOT a drop-in for this
workload: it has no FTS5, its fresh-store schema is not census-equal to
stock SQLite, its default build is single-process, and the measured
workload numbers favor stock SQLite on every axis recorded below. Standard
SQLite remains the only default; nothing here changes any default, and no
drop-in or faster claim is made. Any default change is an owner decision
that would require new evidence.

## 1. What was built for this evaluation

- `Cargo.toml`: optional feature `turso = ["dep:turso", "dep:tokio"]`.
  Default features unchanged; `cargo build` and `cargo test` are green
  WITHOUT the feature (A1 gate), and `cargo build --features turso` is
  green with zero warnings (A2 gate).
- `src/persistence/turso_backend.rs`: full `SessionStore` implementation —
  upstream DDL applied verbatim through a trigger-aware statement splitter,
  §6.1 operations (ensure/append/get/search/end/usage), PASSIVE checkpoint,
  quarantine-free admission (turso 0.8.3 exposes no page-0 header probe
  surface; recorded, not silent).
- `tests/hrs009_backend_parity.rs`: 10-test battery, BOTH backends, same
  assertions (§3 below). `tests/hrs009_crash_child.rs`: kill -9 harness.
- `examples/hrs009_bench.rs` + `scripts/run_hrs009_bench.sh`: the measured
  workload (§2). The runner refuses load average > 4 on the host.

## 2. Measured workload (identical dataset + identical code path)

Harness: `examples/hrs009_bench.rs`, driven by `scripts/run_hrs009_bench.sh`
on **master001** (AMD Ryzen 9 7950X, 32 hardware threads, Debian 13,
kernel 6.12, NVMe, load 0.18 at run time). The kara agent box was EXCLUDED:
it sat at load ~52 during this task (documented host I/O starvation) and
any number from it would be noise, not measurement.

Dataset (both arms open the SAME file, fixed seed, no post-hoc tuning):
- 5,000 sessions, 2–10 transcript messages each (200–500 words/message ≈
  a few KB per session), generated by xorshift64* (seed recorded in the
  JSONs) through the STOCK writer — i.e. the dataset carries the full
  upstream schema INCLUDING the FTS5 indexes the stock backend creates,
  exactly like a real upstream store. 323,117,056 bytes on disk.
- Workload: 10,000 ops, 70% reads / 30% writes fixed by the seed — point
  reads by session id (get_session + message page), ensure+append writes,
  a usage delta every 25th write, PASSIVE checkpoint every 500 writes.

Raw results: `benchmarks/results/hrs009-stock.json` and
`benchmarks/results/hrs009-turso.json` (checked in; regenerable with
`sh scripts/run_hrs009_bench.sh <repo>` on any idle Linux host).

RESULTS:

| Metric | Stock SQLite (rusqlite 0.40.2) | Turso 0.8.3 |
|---|---|---|
| Ops completed / attempted | 10,000 / 10,000 (0 errors) | 49 / 10,000 — **0 writes landed; harness error circuit-breaker stopped the run** |
| Wall clock | 1.00 s | 1.75 s (for the 49 ops it managed) |
| Throughput | 9,978.5 ops/s | 28.1 ops/s (non-comparable: run aborted) |
| Read p50 / p95 / p99 | 0.042 / 0.057 / 0.064 ms | 35.3 / 38.1 / 39.8 ms |
| Write p50 / p95 / p99 | 0.175 / 0.296 / 0.819 ms | no writes committed (error path) |
| Peak RSS (VmHWM) | 7.6 MB | 38.4 MB |

The turso arm's 35–40 ms reads and the aborted writes have one measured
root cause (§3.2): the dataset is a real Hermes-shaped store WITH FTS5
objects, and turso 0.8.3 mis-handles schema resolution on such files —
every `ensure_session` upsert fails with `Parse error: ON CONFLICT clause
does not match any PRIMARY KEY or UNIQUE constraint`, and reads degrade to
full-scan costs. That is not a tuning problem; it is the compatibility
result, published as-is per the brief. The honest comparison of engine
speed on a turso-CREATED schema is additionally recorded: on a fresh
turso-created store (no FTS5, probe 10) the same upsert works — so the
numbers above are the ones that matter for Hermes (real files), and the
turso-on-turso numbers would describe an engine that cannot host upstream
data anyway.

**Honest losing number: Turso is the loser on p95 — on the identical
Hermes-shaped workload its read p95 is ~670× stock SQLite's (38.1 ms vs
0.057 ms) and it committed ZERO writes before aborting on its own
schema-resolution failure (exact values in
`benchmarks/results/hrs009-turso.json` vs `hrs009-stock.json`).**

|---|---|---|---|

| 2 | insert/read round-trip through the shim | pass | pass |
| 3 | transaction rollback all-or-nothing (failed txn discards ensure) | pass | pass |
| 4 | indexed point reads over 200 sessions (<500 ms envelope) | pass | pass |
| 5 | WAL journal capability + PASSIVE checkpoint + post-checkpoint durability | pass (real WAL) | pass (journal_mode read-back "wal"; checkpoint via `PRAGMA wal_checkpoint(PASSIVE)` returned (0, 8, 8)) |

Additional measured facts recorded by the probes underpinning this battery:

### 3.1 Upstream DDL fidelity
`UPSTREAM_SCHEMA_SQL`: 25/25 statements apply on turso 0.8.3 (tables,
AUTOINCREMENT, CHECK constraints, partial indexes, the
`idx_sessions_effective_activity` expression index, views).
`UPSTREAM_DEFERRED_INDEX_SQL`: 6/6 (including the
`messages_message_uid_insert` trigger with a BEGIN..END body). The
mint expression `lower(hex(randomblob(16)))` works. `UPSTREAM_FTS_SQL`:
1/9 — the FTS5 virtual tables are the failure (§3.3).

### 3.2 File format
Turso 0.8.3 writes the verbatim `SQLite format 3\0` header. Bidirectional
probe: a turso-written file was read AND written by the system sqlite3
3.53.4 CLI (`PRAGMA integrity_check` = ok), and sqlite3-written rows were
read back by turso. HOWEVER, interoperability is broken in BOTH
directions once real upstream schemas are involved:

- **Turso → upstream files (the deal-breaker): a file that contains FTS5
  virtual tables — i.e. any real Hermes/upstream database — breaks
  Turso's schema handling engine-wide.** Minimal reproduction (probe 13,
  committed evidence in this tree's history): a file with a plain
  `CREATE TABLE t (id TEXT PRIMARY KEY, …)` plus one
  `CREATE VIRTUAL TABLE fts USING fts5(content …)`, both created by stock
  sqlite3. Reopened in Turso, an `INSERT … ON CONFLICT(id) DO UPDATE` on
  the plain table fails with `Parse error: ON CONFLICT clause does not
  match any PRIMARY KEY or UNIQUE constraint` — the PK index of an
  unrelated table stops matching once an FTS5 object exists in the
  schema. The identical upsert succeeds on the same file when sqlite3
  runs it, and on a turso-created file with the same DDL minus FTS5. This
  surfaced in the benchmark itself: the turso arm committed only 49 reads
  and 0 writes out of 10,000 ops before the harness's error circuit
  breaker stopped it (all failures were this parse error on
  `ensure_session`'s upsert against the stock-scaffolded dataset).
- **Upstream → Turso files**: a turso-created fresh store lacks every FTS
  object (no fts5 module — §3.3), so it is NOT census-equal to a
  stock-created store (recorded as a degraded note at open), and upstream
  search SQL has no index to hit.

### 3.3 FTS5 — the hard blocker
Turso's FTS is an index METHOD named `fts` (source: turso_core 0.8.3
`ext/mod.rs`, `FTS_INDEX_METHOD_NAME = "fts"`), not the SQLite `fts5`
module. The crate's default `fts` cargo feature does not provide fts5
syntax. Consequences: upstream search SQL (`snippet()`, `bm25()`, MATCH
against `messages_fts`) cannot run; the shim's search serves canonical
rows via LIKE only (no BM25 ranking, no snippet, no trigram). This alone
rules Turso out as a Hermes-compatible backend at this version.

### 3.4 Concurrency model
Default build = single process: a second PROCESS opening the same file
fails at open with `Locking error: Failed locking file … File is locked by
another process` (probe 4). `experimental_multiprocess_wal(true)` exists
but was NOT enabled or evaluated for this slice (out of scope; would need
its own durability battery). SQLite's multi-process WAL — which upstream
Hermes relies on (multiple gateway backends, CLI + gateway) — has no
equivalent in the default turso build. Same-process concurrency (what the
battery tests) works with `database is locked` surfaced as a busy error
under BEGIN IMMEDIATE contention, matching the shim's error taxonomy.

### 3.5 Transaction semantics
BEGIN IMMEDIATE / COMMIT / ROLLBACK via raw SQL work; the Transaction
(drop-rollback) API also works; upserts (ON CONFLICT DO UPDATE) work;
`last_insert_rowid` works. One observed deviation: `execute("PRAGMA x = y")`
errors with `unexpected row during execution` — row-returning pragmas must
go through `query()`. The backend encapsulates this; callers never see it.

### 3.6 Kill -9 durability
Writer process commits 100 individual transactions then dies by SIGKILL:
80 rows durable and correct on reopen (the process was killed mid-burst;
rows committed before death survived, ids contiguous, no torn rows).
Commits were SLOW (100 individual BEGIN/COMMIT cycles took tens of
seconds on the loaded probe box; see §2 for the clean-host numbers) —
consistent with per-commit fsync behavior in the async I/O path.

## 4. PostgreSQL scope decision

**PostgreSQL stays OUT of scope.** AC-4 requires, for an optional
PostgreSQL backend, that "SQLite↔PostgreSQL import/export tools preserve
supported data" — that is a migration-round-trip program (schema
translation for ~60 session columns incl. REAL-epoch/TEXT/JSON-as-TEXT
conventions, AUTOINCREMENT rowid semantics, partial + expression indexes,
triggers, FTS5 virtual tables, import/export with integrity checks and
rollback after new writes). Nothing in this task's evidence reduces that
work: it is a separate, sizeable deliverable (HRS-003 proved Python reads
SQLite files directly, so any PostgreSQL path would also break the
file-compatibility baseline the Python reference depends on). Per the
contract: PostgreSQL remains "an optional deployment choice, not a
mandatory migration" — and until the round-trip work is separately
resourced and approved, it is not pursued.

## 5. Recommendation (and what it does NOT claim)

1. **Keep stock SQLite as the only backend and the compatibility
   baseline.** It wins the measured workload, and it is the only backend
   with FTS5, backup-API snapshots, and multi-process WAL.
2. **Do not adopt Turso 0.8.3** for Hermes session storage: no FTS5
   (blocker), single-process by default (blocker for upstream-shaped
   deployments), fresh-store census mismatch, slower writes. Re-evaluate
   only when turso ships fts5 compatibility + multiprocess WAL by
   default, and re-run this exact harness (it is committed and
   reproducible).
3. **PostgreSQL: deferred** per §4; no implementation, no migration
   tooling, no claims.
4. This evaluation makes NO default switch, NO drop-in claim, and NO
   general performance claim about any engine. The only performance
   statements are the checked-in numbers from §2 on the named host with
   the named seed.
5. Follow-up candidate (optional, NOT filed as a claim): run the same
   harness at larger N (50k+ sessions) and with `experimental_multiprocess_wal`
   to complete the concurrency picture if the owner wants the Turso
   question closed exhaustively; ROADMAP Gate 7 wording is otherwise
   satisfied by this document.
