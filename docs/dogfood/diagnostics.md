# hermes-rs — diagnostic trail (dogfood run 2, 2026-10-17)

Explained lessons, not raw logs. Raw captures live in
`docs/evidence/dogfood-20261017/`. Findings: `DF-HRS-104..111` on
`.coding-hermes/board/tasks.jsonl`.

## 1. How this thing is put together (and why)

```
Cargo.toml ─┬─ lib  hermes_rs              src/lib.rs (scaffold_status)
            ├─ bin  hermes-rs              src/main.rs  (prints the status line)
            └─ bin  hermes-rs-session-adapter  src/bin/session_adapter.rs
                                              stdio JSON-RPC server (520 lines)

src/persistence/
  api.rs            engine-neutral contract: SessionStore/WriteTxn/ReadTxn,
                    PersistenceError taxonomy, OpenOptions/OpenReport/Capabilities
  stock_sqlite.rs   the only default backend (rusqlite `bundled` — SQLite is
                    compiled in, so file behaviour does not drift with the host)
  turso_backend.rs  OPTIONAL feature `turso` (evaluated, NOT adopted — HRS-009)
  upstream_ddl.rs   upstream's DDL verbatim: schema, FTS5 base + trigram,
                    deferred indexes, and FRESH_STORE_CENSUS_JSON
```

Design commitments that shaped everything: the store is engine-neutral behind
`api.rs`; the Python seam is a **process boundary** on purpose (PyO3 and C-ABI
were rejected in `specs/python-interop.md` §3.5 so no consumer can mistake it
for an embed and no CPython version claim is implied); and the FTS index is a
*derived* structure — canonical rows are `messages`, `messages_fts` is
sync'd by triggers, and the code has explicit arms for a stale or corrupt index.

## 2. The right way to drive it (what this run established)

1. Build the boundary binary: `cargo build --release --bins` →
   `$CARGO_TARGET_DIR/release/hermes-rs-session-adapter`. **`CARGO_TARGET_DIR`
   is set fleet-wide on this host (`/var/tmp/hermes-cargo-target`)** — a bare
   `cargo build` exits 0 and writes nothing to `./target`, so always resolve the
   binary from `$CARGO_TARGET_DIR` (the repo's own proof driver does this too)
   and check its mtime against `git log -1` before trusting a result.
2. Speak §4 verbatim: one JSON object per line on the adapter's stdin; one
   reply line per request; `hello` reports `protocol`, `knows_schema_version`,
   `language`, `boundary`. Errors arrive as `{"error":{"error","cause","detail"}}`
   — never parse stdout for prose.
3. `open` takes `path` (required), `create`, `read_only`. **`create` defaults to
   false and a wrong type is silently ignored** (a string `"yes"` or `1` is
   treated as absent), so a fresh path with no `create=true` fails as
   `Io: unable to open database file` with no hint about the missing flag.
   Pass all three explicitly.
4. One store per process; `close` drops the handle, `shutdown` exits 0. An
   unknown method exits 6 **by design** (fail-closed) — a client must detect the
   dead child itself (`poll()` before writing) or the next call dies with a
   broken pipe, even though §4 lists `ProcessDead` as a client-side code.
5. `checkpoint` is PASSIVE-only; `backup` writes a page-consistent snapshot but
   refuses a destination that already exists (`DF-HRS-108`).

## 3. Errors hit on the way — and what they teach

| symptom | cause | right way |
|---|---|---|
| `Io: unable to open database file` | `create` omitted / wrong-typed → defaults false | pass `create=true` explicitly |
| `Io: backup destination exists` | second snapshot to the same path | use a fresh destination per run today; row filed |
| `BrokenPipeError` after probing an unknown method | unknown method = documented exit 6 | check `poll()` between calls |
| `fts5: syntax error near "/"` when SQL-matching raw user text | FTS5 grammar is not free text | compare against the store's *sanitized* query, not the user's |
| `cargo test` red on a fresh box (5 tests, `Os code 2`) | tests shell out to a system `sqlite3` CLI | document/preflight it; row filed |
| `git status` dirty after any test run | a tracked evidence file is regenerated by the suite | row filed (`DF-HRS-111`) |

## 4. Where the search defects come from (anatomy, not blame)

`sanitize_fts5_query` (`stock_sqlite.rs:1026-1126`) was ported from upstream's
`_sanitize_fts5_query` to make arbitrary user text safe for an FTS5 `MATCH`.
It runs six steps; two of them change meaning instead of making the string safe:

* **step 2** (line 1049) filters the FTS5-special set out of the string with no
  replacement, so `src/main.rs` becomes the single token `srcmain.rs`; **step 5**
  (line 1093) then quote-wraps any word containing `. - _`, so the merged token
  becomes a *phrase* that cannot match. Deleting a separator is not the same as
  neutralising it — a space preserves the user's intent (`DF-HRS-105`).
* **step 4** (line 1079) is meant to drop a *dangling* boolean operator at the
  head or tail of the query, but tests `starts_with`/`ends_with` on the whole
  string, so it eats the first three characters of any leading word beginning
  with `and`/`or`/`not` (`notes` → `es`, `brand` → `br`) and the last three of a
  trailing word ending with them (`command` → `comm`). A whole-token comparison
  is the fix (`DF-HRS-104`).

Neither path reports that it rewrote the query, and the "syntax error despite
sanitisation" arm returns `Ok(vec![])` — so a mangled query and a genuine miss
are the same answer. When a silent-rewrite step exists, the product needs either
a LIKE fallback on zero hits or a machine-visible marker that the query changed.

**Why the repo's own tests did not catch either:** the HRS-003 proof searches
nothing (`tests/hrs003_python_interop.rs` covers create/append/read/reopen/
backup/error/lifecycle), and the HRS-010 suite's FTS leg asserts on queries
built from its own fixtures (`sqlite`, single words), i.e. inputs the sanitizer
leaves alone. The defect class is "input the author did not type" — exactly what
a dogfood run supplies.

## 5. The fresh-store report (why it looks contradictory)

On a brand-new path the store *does* scaffold upstream's DDL, and it *does* run
a census check afterwards comparing `sqlite_master` against
`FRESH_STORE_CENSUS_JSON` (`stock_sqlite.rs:167-185`, called at `:446`). The
census expects 26 indexes; the scaffold creates 24 — the two missing names
appear nowhere else in the repo — so the check fires and the report carries
`degraded: ["fresh-store census mismatch after scaffold"]`. At the same time the
`created_new_store` **local** is set (`:402`) and used for the `fts_storage_version`
seed (`:438`) while the **report field** is never assigned (`OpenReport` comes
from `::default()` at `:319`), which is why the JSON says `false` on a
first-ever create. Two independent omissions in the same return path; both are
observable only by opening a store that does not exist yet.

# Addendum — dogfood run 3 (2026-10-20, HEAD `7331204`): the slice as a Rust library, from an archive importer's seat

Run 2 drove the Python boundary; this run wrote a **Rust consumer outside the repo**
(`hrspack`, source in `docs/evidence/dogfood-20261020/`) and used the library the way a
user would: pack 200 Hermes-shaped sessions (4,000 messages) into a state.db-compatible
archive, search it, record usage, snapshot it. Full report:
`docs/dogfood/2026-10-20-run3-integration.md`.

## 1. What the slice does now (verified, not claimed)

The eight defects run 2 filed (`DF-HRS-104..111`) are closed, and this run re-proved every
fix from the consumer side: word-class search (`notes` 610/610, `brand` 658/658), specials
and paths (`src/main.rs` 854/854, `state.db` 979/979, `C++`, `O'Brien`), a fresh store that
reports `created_new_store=true degraded=[]`, `backup` overwriting an existing destination,
a suite that skips (with a recorded reason) instead of failing when the `sqlite3` CLI is
absent, and a tree that stays clean after `cargo test`. Content fidelity is byte-exact:
4,000/4,000 messages round-tripped through the Rust writer and were read back with the
system sqlite3 (a different SQLite build) — CJK, emoji, accents and punctuation included.
The wiring is real end to end: the file the Rust consumer wrote is read by the stdio
adapter with the same counts and snippets.

## 2. The lesson this run adds: the shim is a *live session* API, not an *archive* API

`ensure_session(session_id, source, model)` has no timestamp parameter on either surface,
so every imported session is stamped with the import wall-clock: the corpus said
`started_at=1760900000`, the store answered `1792510163.87`. A session's `started_at` can
therefore come out **later than the timestamps of its own messages**, and since upstream's
time-window routes bound `sessions.started_at` (spec §2.3/§2.4), any date-filtered query
over an archive is meaningless. The same shape shows up one table over:
`record_model_usage` writes the per-model rollup and folds it into the session projection,
but no `ReadTxn` method and no adapter method returns the rollup — the repo's own test reads
it with raw `rusqlite` SQL. Neither is a crash; both are the boundary of what the slice
claims, and neither was documented anywhere a consumer would look. Filed as `DF-HRS-115`.

## 3. Two artifact-hygiene defects found while using the thing

- The adapter's `open` validates its flags with `as_bool()` + a default of `false`
  (`src/bin/session_adapter.rs:502-515`), so `create: "yes"` / `create: 1` are treated as
  absent (the user sees only `Io … unable to open database file`) and `read_only: "true"`
  is treated as **false** — the store opens read-write. Run 2 recorded the `create` half in
  `params.log` but never filed it; the `read_only` half is new. `DF-HRS-114`.
- The skip log (`$CARGO_TARGET_DIR/hrs010-skipped-tests.log`) held 5 records in 4 lines:
  `writeln!` through an `OpenOptions::append` handle is not one atomic write, so two test
  threads interleaved mid-record (`…verification)SKIPPED: f9_…`). `DF-HRS-116`.
- Not the archive tool's fault, but found while validating this run's own work: the
  project's `events.jsonl` (the board's event log next to `tasks.jsonl`) carries a **fused
  record** at line 22 (two JSON values on one physical line, 475 trailing bytes), which
  makes `boardctl validate -C .` answer `RESULT: FAIL (1 error(s), 18 warning(s))` on the
  committed blob. It also makes the board's own writer unusable: `boardctl event` printed
  the same error and appended nothing, so the measurement event this run intended to attach
  to `DF-HRS-112` (see §4) could not be filed and lives in this document instead.
  `DF-HRS-117`.

## 4. Performance is measured, not asserted — and no PERF row is justified

Cold build of a consumer from scratch: **83 s** (rusqlite `bundled`). Cold store creation
(full upstream DDL + FTS scaffold): 1.19–1.40 s clean, 3.0–4.4 s under load. Warm open of a
4,000-message store: 0.06 s clean. Import of 4,000 messages: 4.5–17.3 s, with **user CPU
1.0–1.3 s** in every run (≈0.3 ms/message — the wall time is commit I/O, not the store's
compute). End-to-end CLI search: 127–169 ms wall, 6–18 ms user, with the in-process query
at 1.3–14.5 ms. Nothing a user would feel, so no `PERF-<n>` row: the honest statement is
that the wall numbers swing up to 4× with host load (load 9–23 on 16 cores, plus a
concurrent fresh-build battery on a bunker agent), and the CPU column is the stable signal.
One measured correction to the batch story: at the Rust API level with one transaction per
session, `append_messages_batch` and a loop of `append_message` are indistinguishable — the
batch surface's value is eliminating per-message **round trips on the wire** (the 11.7× in
`docs/evidence/hrs109/batch-2000-wire.log`), not per-message cost inside a transaction.
Attached as an event on `DF-HRS-112`, not as a new row.

# Run 4 (2026-10-23) — scale, the wire client, and a guard that cannot see behaviour claims

## 1. What this run added

Run 3 proved the slice on a 4,000-message corpus and on the Rust API. Run 4 drove the
**documented Python boundary** with a 60,000-message archive across 300 sessions, and
re-checked the project's own coaching against HEAD. Everything below is from captured
output in `../evidence/dogfood-20261023/`.

## 2. How the numbers were produced (so they can be re-run)

`run_user_flow.py.txt` imports the repo's own `scripts/hrs003_client.py` — nothing private —
generates a deterministic corpus (seed `20261023`), plants each of ten "needle" strings in
exactly four messages, and grades search against those known slots instead of against the
product's answer. `tail_stages.py.txt` re-opens the store the first script left behind, so the
reopen number is a genuinely cold process. `probe_open_flags.py.txt` speaks raw frames.

Two probe-harness bugs of my own, fixed before their results were used, worth recording
because each one *looks* like a product defect:

1. I read search hits as `h["content"]`. The wire returns `snippet` (with `>>>match<<<`
   highlighting), so every hit looked empty. Inspecting one raw frame showed the real
   shape; nothing was filed. Read one frame before writing a parser.
2. The documented reference client has **no `get_session`** even though
   `specs/python-interop.md` §4 lists it, so my first run died with `AttributeError`
   halfway through — that became `DF-HRS-119`, but only after confirming the method exists
   on the wire (`a._call("get_session", …)` answered) and is merely missing from the client.

## 3. Why the skill drift happened, mechanically

`scripts/check_skill_claims.py` (the DF-HRS-113 guard) walks every `DF-HRS-<n>` citation in
`skills/hermes-rs-usage/SKILL.md`, resolves its row status, and fails only when the claim
sentence matches a **staleness marker**: `open`, `still`, `yet`, `workaround(s)`,
`do not trust`, `until fixed`. Its own docstring says a claim carrying none of those
markers is let through — "the guard does not guess semantics".

The stale sentence at HEAD was:

> **The adapter's `open` ignores wrong-typed flags.** … `create: "yes"` / `1` behave as
> absent → `Io: unable to open database file` with no hint, and `read_only: "true"` is
> treated as **false** … (`DF-HRS-114`).

No marker word appears; the row it cites is `complete`; the sentence is a confident
present-tense assertion about current behaviour. So the guard passed (`rc=0`) while the
prose described the pre-`04822cc` code. The timing is the tell: the skill was rewritten at
11:15 on 2026-10-20, the adapter fix landed at 11:29 — **fourteen minutes later** — and
nothing re-read the prose.

The lesson for this repo: a doc guard that models drift as *row status vocabulary* cannot
see drift as *behaviour*. A claim that names a closed row and states what the code does
should be graded by a probe (or by a marker vocabulary that includes present-tense
behaviour verbs like "ignores", "treated as", "behave as"), not only by "open/still/yet".
